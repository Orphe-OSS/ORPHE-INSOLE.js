## [Unreleased]

### Added

- `examples/gait-report/` — a measurement-session example that turns Step Analysis into a one-page gait report, listed on the landing page, the examples index, and the sitemap. Press **Start recording**, walk, and the report updates on every step; once **20 steps per foot** are collected the report is finalized as mean ± SD (a single connected foot completes on its own 20 steps; sides are resolved from `device_information.mount_position`, and a side that is connected but silent keeps the session open). The report shows basic gait measures for both feet (speed, cadence as 120 ÷ gait cycle, stride length, gait cycle, stance %) with n and display-only reference ranges, per-side gait-cycle variability (CV%), a left/right comparison (stride, stance and swing time, landing force) with a signed asymmetry percentage — pronation is compared as a degree delta instead of a percentage because it is a signed angle — and per-side foot-strike / pronation-class counts. By design it renders **no scores and no pass/fail judgments** (reference ranges are labeled as informational only), and FW `-1` sentinels exclude only the affected parameter from aggregation. Includes the standard example template (JA/EN i18n, in-header Toolkit slots, `realtime-full-step` profile, auto-playing synthetic demo that completes a session in about 20 s, `?demo=0` opt-out), a print stylesheet that prints just the report card, a `?verify=0` diagnostic mode that keeps the connection alive without Step Analysis liveness verification (used to isolate the FW 1.0.1 no-notification issue), and pure aggregation logic in `examples/gait-report/report.js` covered by `tests/gait-report-stats.test.js`. Verified on hardware (FW-updated pair, both feet, 20/20 steps, 54 s session).
- `OrpheInsole.getFirmwareVersion()` — resolves the device firmware version as a string, first from the standard BLE Device Information Service (0x180A, now included in `optionalServices`; Firmware Revision String with Software Revision String fallback), then from the advertisement-derived `insole.lastStatus.version`; returns `null` instead of throwing when neither source is available (some current firmwares do not implement 0x180A, and advertisement watching requires a `watchAdvertisements()`-capable browser). `onAdvertisementReceived` now always stores the parsed status as `insole.lastStatus` (even when no `gotStatus` callback is set) and guards against manufacturer data shorter than the version bytes. The result is cached in `insole.firmware_version` and cleared when a different Bluetooth device is selected. The simulator implements the same method (returns `"simulator"`), and TypeScript definitions are updated.
- `InsoleToolkit`: the connection header now shows a firmware badge (`FW x.y.z`) when the version can be resolved, and the settings modal gains a Firmware row. Firmware versions with no confirmed STEP_ANALYSIS output are listed in the exported `INSOLE_TOOLKIT_STEP_UNSUPPORTED_FW` (currently `1.0.1`, measured 2026-08 on two units that stayed at zero transport notifications while Raw streamed normally at 50 notifications/s): enabling Step Analysis on such firmware turns the badge to a warning color, logs a `console.warn`, and emits a `fw-step-analysis-unconfirmed` gait diagnostic — as a triage hint, not a hard block. `GAIT_NO_NOTIFICATIONS` errors now state that the firmware may not support Step Analysis output, include the firmware version when known, and carry it as `error.firmwareVersion`. Documented in `docs/TROUBLESHOOTING.md` (section 3b) together with the Chrome flags needed to read versions from advertisements.

## [1.3.1] - 2026-08-02

### Fixed

- `OrpheInsoleFifo.stop()`: recover the forward backlog that was never requested when recording stops while the host is behind (**catch-up**). The previous recovery phase (`drain`) only re-requested serials it had already asked for and not received (`carryOver`); it never requested serials the firmware had already produced but the host had not asked for at all, and that shortfall was counted in neither `missing` nor `droppedCount` — so a recording could be silently several seconds short of the requested span while still reporting zero loss. Measured with two devices recording the same span simultaneously, the lagging device consistently captured only 86–89% of it with `missing=0, dropped=0`. `stop()` now freezes the firmware's current serial as a fixed target the moment it is called, issues new range requests up to that target before falling back to draining outstanding `carryOver` re-requests, and counts whatever cannot be retrieved within `drainTimeoutMs` as `stopped_pending` in `droppedCount`. `onStopped(info)` gains a `catchupRecovered` field alongside the existing `drainRecovered`. This restores the invariant that `missing === 0 && dropped === 0` means the full recorded span is actually present. `options.drainTimeoutMs` now behaves as an idle budget shared by both recovery steps (extended while data keeps arriving, capped by an absolute upper bound) instead of a single fixed deadline, so a normal loss-free stop still returns immediately.
- `OrpheInsoleFifo`: correct the per-frame timestamp spacing used inside a data packet. `decodePacket()` and `packetToCsvRows()` both assumed a 200 Hz sample rate (5 ms/frame); measuring packet-to-packet cadence on real hardware over roughly 1,500 packets on two devices shows the IMU's actual output data rate is close to the LSM6DSOX's standard 208 Hz (≈4.808 ms/frame), about 4% faster than assumed. Left uncorrected, this stretches intra-packet sample timing and can produce a zero or negative time delta between consecutive samples at packet boundaries — silently skewing anything that integrates using per-sample `dt`. `decodePacket()`'s sample `t` now uses a `FRAME_INTERVAL_MS` constant derived from a new `IMU_ODR_HZ` (208) constant, both exported as statics. `packetToCsvRows()`'s per-row timestamp string intentionally keeps the previous 5 ms spacing — now a named `LEGACY_CSV_FRAME_INTERVAL_MS` constant — for byte compatibility with the Python reference implementation's CSV format and with existing recorded CSVs; see the updated notes in `CLAUDE.md` / `docs/SENSOR_SPEC.md`.

## [1.3.0] - 2026-07-28

### Added

- `examples/udon/` — a stepping game ("おいしいうどんを作ろう！", a port of the older 4ch-FSR `UDON_fsr_20250724` project) that shows how to build event-driven detection without any calibration step. A step is detected in two stages: foot lift from `gotConvertedAcc` / `gotConvertedGyro` (`|accY|`, `|accZ − 1G|`, gyro magnitude) while the load is off, then the stomp from `gotPress`. Because the 6ch ADC values carry a no-load offset of roughly 220 per channel (about 1358 in total on device `00000161`/left), absolute thresholds break across devices and fits — so every threshold is expressed as `delta = 6ch total − no-load baseline`, where the baseline is the minimum total over the last 4 seconds tracked in 500 ms buckets and follows the wearer automatically. Each step is scored (lift height × stomp delta × timing, a weighted sum tuned on a 34-step device log) and classified TOO WEAK / WEAK / GOOD / EXCELLENT / PERFECT, with left/right balance and pace advice; left and right are resolved from `mount_position`. Runs on `profile: "realtime-pressure"` (mode 3, 200 Hz), plays synthetic data until a device connects, ships JA/EN, fullscreen, live threshold tuning with presets persisted in `localStorage`, and two CSV exports (per-step events, and per-frame raw data while recording) for deriving thresholds from real logs.
- `examples/exhibition/` — a booth/demo page that fits the whole story on one 16:9 screen with no scrolling: the 6ch foot pressure map with CoP for both feet, the TOTAL PRESSURE gauge (total + left/right), acceleration and gyroscope charts per device, and the quaternion 3D attitude view with Euler readouts. Falls back to looped synthetic walking data until a device connects, auto-reconnects during a show, orders panels by `mount_position` so the left foot stays on the left, and has a fullscreen button plus attitude reset for stage setup. Visualization is reused from the showcase modules (`viz-pressure` / `viz-imu` / `viz-3d` / `demo-data`) rather than duplicated — those now accept `window.ORPHE_SHOE_MODEL_BASE`, `window.ORPHE_ATTITUDE_ZOOM`, and a placeholder-height-driven canvas so they can be embedded in a fixed layout. The pitch/roll swap defaults to on here (correct for FW 202605 hardware).
- `examples/showcase/`: a "Swap pitch / roll" switch in the Attitude (quaternion → 3D) section. Depending on the firmware / IMU axis assignment, lifting the toe can show up as roll — `quaternion.js` reports `roll` for X-axis rotation while the INSOLE frame has X pointing right and Y toward the toe. The switch (off by default, bilingual) applies a similarity transform that rotates the sensor frame -90° about Z (`q' = r q r*`, `SWAP_R` in `viz-3d.js`), so **both the 3D model and the Euler gauges** flip together; the gauges are recomputed from the transformed quaternion so they can never disagree with the CG. CSV recording keeps the raw SDK values. The rotation sign was verified against a physical device: +90° exchanges the axes correctly but reverses both rotation directions (lifting the toe raises the heel in the 3D view).
- `examples/fifo-guide/` — a beginner-oriented public example for FIFO (buffered) recording, listed in the examples index and on the landing page. One physical insole, one page: connect → pick a duration (10 / 30 / 60 s or a custom value) → record → wait for drain → review continuity → export. It explains Realtime push versus FIFO serial-addressed pull, that FIFO Raw carries gyro/acc/pressure but no quaternion, that FIFO Raw and Step Analysis are used sequentially on the current firmware, that a recording completes only after the post-stop drain, and that one FIFO serial packet is four CSV rows. The **~30 s device buffer** is documented with its derivation from SDK constants (`RING_BUFFER_CAPACITY` 1500 packets × 4 frames × 5 ms = 30,000 ms) and is explicitly **not** presented as a no-loss guarantee: runs longer than 30 s are supported and marked as a caution band, and shorter runs can still lose data when polling falls behind. `dropped` (cumulative unrecoverable-loss events during the run) and the final CSV window's `missing` (serials absent from the exported range) are shown as separate metrics with separate explanations. Continuity is rendered as a Canvas timeline aggregated into a fixed number of bins (no per-serial DOM nodes) plus exact `1200–1208`-style missing ranges, handling uint16 65535→0 wraparound, duplicate serials, and out-of-order drain recovery; the page also re-derives the loss count from the exported CSV and logs whether it matches the on-screen value. Colour-independent PASS/WARN/FAIL labels, bounded live buffers, a copyable event log with environment details, and Raw CSV / result JSON exports gated on drain completion. The page uses only the public API (`buildInsoleToolkit` with the `fifo-recording` profile, `startMeasurement()` / `stopMeasurement()`, `insoleToolkitMeasurementToCSV()`) and re-implements no part of the FIFO protocol; its decision logic lives in `examples/fifo-guide/continuity.js` and is covered by `tests/fifo-guide-continuity.test.js`, which also verifies the 30 s derivation against `src/InsoleFifo.js`. The page follows the same example template as `examples/step-analysis/` — shared header (back link, JA/EN switch, in-header Toolkit slot), control strip with a state badge, Toolkit settings guide, dark chart cards, table frame, scope note, and code card — and is bilingual through `examples/fifo-guide/i18n.js` with `?lang=ja` / `?lang=en` plus timezone-based defaulting. Verified on hardware (single device, 30 s, missing 0 / dropped 0, CSV cross-check matched), which surfaced two reporting fixes: the buffer-window verdict now allows a 1 s tolerance so a run of the recommended 30 s is not flagged as over-buffer by stop-timer jitter, and a **recorded span** metric reports the time the CSV actually covers (recorded serials × 20 ms) because serials still unrequested when recording stops fall outside the span — a shorter tail rather than loss, explained separately from `missing`. A 60 s run on the same hardware reproduced the documented limit (`maxLag` 1129 of 1500, four serials lost as `fw_nodata`, `missing` 4 / `dropped` 4, recorded span 42.9 s of 60 s), and both observed runs are recorded in the example README as environment-dependent measurements rather than guarantees. The page also records **one or two devices at once**: both measurements start and stop together, serial continuity, loss, lag, and span are tracked and displayed per device (per-device timeline cards and result-table columns, left/right resolved from `device_information.mount_position` rather than device index), the overall verdict combines the per-device verdicts worst-first, both devices are exported as a single CSV keyed by `device_id`, and a dual-device run adds guidance to compare a one-sided loss against a single-device baseline because host Bluetooth load alone can cause it.
- Named `InsoleToolkitSession` measurement profiles (`realtime-orientation`, `realtime-pressure`, `realtime-full`, `realtime-full-step`, `step-analysis`, `fifo-recording`) plus atomic `configure()` / `applyProfile()` transitions. `startMeasurement()` and `stopMeasurement()` now define a stable recording window across Realtime, FIFO, and Step Analysis; reject profile changes while recording; wait for FIFO drain; return serial-loss summaries and bounded Raw/Step records; and export the selected window through `insoleToolkitMeasurementToCSV()`. The existing individual setters remain backward compatible and delegate to the same serialized transition path.
- `OrpheInsole.addSensorDataListener()` / `removeSensorDataListener()` for independent decoded Realtime packet observers that coexist with legacy `gotData` and `got*` callbacks. The simulator implements the same observer API, and `ORPHE_INSOLE_STREAMING_MODES` is the shared source for realtime format metadata.
- `OrpheInsoleFifo` measurement checkpoints (`createCheckpoint()` / `summarizeSince()` / `serialsSince()`) so a formal FIFO run can be evaluated by the device-serial range requested after its start, instead of by host callback arrival time. The manual toolkit validator now keeps both views and uses the checkpoint result for the verdict, preventing preview packets recovered before the window and delayed/re-requested packets recovered during drain from creating phantom in-window loss.
- `InsoleToolkit` data-mode controls — the settings modal now independently selects Sensor Values and Step Analysis (including Realtime Raw + Step together), switches Sensor Values between Realtime and FIFO, and keeps the existing realtime format selector (1/3/4). `InsoleToolkitSession` serializes transitions, shares FIFO/Gait ownership with application UIs, drains FIFO before disconnect/reset, and reapplies the selected outputs after reconnect. FIFO and Step Analysis remain opt-in and are enabled when `InsoleFifo.js` / `InsoleGait.js` are loaded. The Showcase recording controls now use the same session instead of constructing competing module instances.
- Unlisted `examples/data-modes/` engineering inspector and measurement harness, retained at its direct URL but intentionally omitted from the public examples index. It documents SENSOR_VALUES Notification, FIFO Request–Response polling, and STEP_ANALYSIS Notification; uses the same named profile/measurement API shown in its copyable code; compares streaming modes 1/3/4, FIFO continuity/checkpoint/drain, STEP_ANALYSIS-only, Realtime Full + STEP_ANALYSIS, dual-device Host load, and reconnect restoration; and exports the formal measurement window as Result JSON, Raw CSV, or Step CSV. The old manual URL remains as a compatibility redirect.
- `src/InsoleGait.js` (`OrpheInsoleGait`, opt-in) — real-time gait analysis. The INSOLE firmware (GaitAnalysisCore / StrideAnalyzer) computes per-stride gait parameters and publishes them on the Gait Analysis service's Step Analysis characteristic (`4EB776DC-…`, the core SDK's `ORPHE_STEP_ANALYSIS`), auto-notifying at 50 Hz once active — so it only needs subscribing (no read-mode change; the characteristic is under `ORPHE_OTHER_SERVICE`, already in `optionalServices`). A port of the `insole_client` `read_gait_analysis` reference: decodes the 20-byte packets (sub-headers 0=overview / 1=stride / 2=pronation / 4=motion, big-endian incl. float16), aggregates the overview/stride/pronation triplet per `step_number` (each sent twice for reliability) into one gait row with derived metrics (stride length, cadence, speed) and foot-strike / pronation classification, and exposes `onGait` / `onMotion` / `onRaw` callbacks plus reference-compatible CSV export. FW `-1` sentinels on non-negative fields are treated as missing; cadence/speed are computed only from a finite positive duration; and the step aggregator evicts in insertion order so uint16 `step_number` wraparound is handled. The lifecycle keeps one active Gait owner per insole, shares initial/reconnect subscription work to prevent duplicate listeners, lets `stop()` finish while `startNotify()` is pending, and compensates a late subscription with `stopNotify()`. Core auto-reconnect re-establishes STEP_ANALYSIS without clobbering user callbacks; after a manual reconnect, calling `gait.start()` explicitly re-subscribes without clearing collected rows. The core SDK routes STEP_ANALYSIS notifications to it via a `_gaitNotifySink` hook (mirrors `_fifoNotifySink`). TypeScript definitions and a Node unit test (`tests/insole-gait.test.js`) included. Added to the `showcase` example as a "Gait Analysis" panel.
- `OrpheInsoleFifo`: recovery phase (**drain**) on `stop()` — after a manual stop, new-range requests are cut off and only outstanding re-requests (`carryOver`) continue until the FW ring buffer is drained or `options.drainTimeoutMs` elapses (default `3000`, `0` disables = legacy behavior). Recovers the tail losses that otherwise remain even in a normal 1 m / two-device environment (#46). Returns immediately when nothing is outstanding, so `stop()` latency is effectively unchanged when there is no loss. Reports recovered count via `onStopped(info).drainRecovered` and marks in-drain progress with `onProgress(info).draining === true`. Only runs on manual `stop()`; skipped on `stopOnLoss` auto-stop, disconnect, or exception. The `showcase` and `fifo-vs-realtime` examples surface the recovered count and a "recovering after stop" status.

### Fixed

- Gyroscope physical-unit conversion. `gotConvertedGyro` (and `converted_gyro` in the parsed packets) treated the raw int16 as an ideal signed Q15 value and computed `raw / 32768 * range`, which is 61.035 mdps/LSB at ±2000 dps — about 12.8% below the LSM6DSOX datasheet typical sensitivity of 70 mdps/LSB — so every physical angular-velocity value the SDK reported was too small. Conversion now uses the per-range sensitivity (8.75 / 17.5 / 35 / 70 mdps/LSB for ±250 / 500 / 1000 / 2000 dps). Rotation logs of known 90 / 180 / 360° turns previously integrated to -81.56 / -153.14 / -311.14°; with the corrected scale they reach -93.54 / -175.63 / -356.84°, close to the quaternion yaw of -95.25 / -181.48 / -358.09°. The normalized `gotGyro` values (`raw / 32768`), the accelerometer conversion (`/32768 × range`, which already matches the datasheet 0.488 mg/LSB at ±16 g), and all public callback signatures are unchanged. Requires a physical re-check with known-angle rotations, and with any non-default gyro range.
- `OrpheInsoleFifo`: apply the same corrected gyro sensitivity (0.07 dps/LSB, FIFO is fixed at ±2000 dps) to `gyro_*[dps]` in decoded samples and exported CSV. The duplicated formula had the same ideal-Q15 error as the core parser. This is an **intentional** 1.14688× difference from the Python reference implementation (`insole_client`), which keeps the ideal-Q15 conversion; the CSV column layout is unchanged. `tests/insole-gyro-scale.test.js` now pins the core and FIFO conversions to the same coefficient so the duplicated formula cannot drift again.
- The accelerometer and gyroscope range settings returned by `getDeviceInformation()` are now applied when parsing live SENSOR_VALUES notifications (both the `got*` dispatch and `addSensorDataListener()` observers). Previously the parser always assumed the ±16 g / ±2000 dps defaults, so a device configured to another range reported wrong physical values. `OrpheInsoleSimulator` derives its normalized gyro values from the same rule as the real SDK.
- `InsoleToolkitSession`: do not treat a resolved STEP_ANALYSIS `startNotifications()` call as proof that gait data is flowing. Toolkit Step modes now wait for a valid decoded packet, retry by reapplying the streaming mode and resubscribing up to two times, and fail with `GAIT_NO_NOTIFICATIONS` or `GAIT_INVALID_PACKETS` plus transport diagnostics. `OrpheInsoleGait` exposes transport/valid/invalid counters and low-frequency diagnostic callbacks. If Step restoration after FIFO drain still fails, the completed FIFO result remains exportable and the session falls back to Realtime Raw instead of rolling back into a background FIFO run. The Showcase surfaces the failure code, and the two-device restore validator records transport-vs-decode evidence.
- `examples/showcase/`: start FIFO recording through the atomic `fifo-recording` measurement profile so Step-only and Realtime Raw + Step states transition safely to FIFO Raw, then drain and restore the previous Realtime/Step profile on stop. The Toolkit guide and Showcase README now consistently document that FIFO Raw is exclusive with Step Analysis on the current firmware. Added a focused two-device physical validation page at `tests/manual/showcase-fifo-restore/` that automates precondition, FIFO, drain, per-device restoration, and post-restore data checks, with copyable event logs and JSON/CSV evidence exports.
- `examples/data-modes/`: bound long-running live-preview metric buffers and remove spread-based min/max aggregation so leaving the physical-device inspector open for hours cannot overflow the JavaScript call stack.
- `InsoleToolkitSession`: reject lossless FIFO Raw + Step Analysis with `FIFO_STEP_INCOMPATIBLE`, while retaining Realtime Raw + Step as the supported application mode. Real-device validation showed that FIFO read mode suppresses Step publishing, while temporary Realtime windows restore Step motion packets but make the same device serials unavailable from the FW FIFO (`fw_nodata`). The settings UI disables the invalid cross-selection and directs users to sequential FIFO recording then Realtime + Step.
- Bound asynchronous polling in the gait and connection-stability tests so a failed mock expectation reports a timeout instead of spinning indefinitely with `setImmediate()`. The gait test gate now also runs in a child process with a 60-second hard timeout (exit 124), preventing a stuck regression from accumulating CPU-consuming orphan processes.
- `OrpheInsoleFifo.download()`: fix intermittent failures to save the CSV. The object URL was revoked synchronously right after `a.click()`, so the browser could invalidate it before finishing reading the blob and silently drop the download — more likely for larger CSVs (e.g. a lossy capture that drain recovers a lot of data for). The anchor is now appended to the DOM before clicking and the URL is revoked on a later tick.
- `OrpheInsoleFifo`: fix a latent span-tracking bug in `FifoLoopState.noteStored()` (introduced with #44's invariant check) where recovering a serial **earlier** than the first-stored one (e.g. the recording's first serial dropped on the initial request and re-fetched later — common on a lossy link) made `serialDistance()` wrap to ~65535, exploding the recording span and causing `finalizePendingLoss()` to report a phantom loss of ~65,336 serials. The span origin now rolls back (wrap-aware min/max) so early-serial recovery no longer inflates `droppedCount`.
- `OrpheInsoleFifo`: re-requests no longer converge-fail mid-recording. Two fixes: (1) `_receiveResponses` now returns after a short quiet period (`ONE_SHOT_IDLE_TIMEOUT_MS`) once a burst has started, instead of blocking the full 5 s `ONE_SHOT_TIMEOUT_MS` on every cycle that has a single dropped packet (which inflated lag and starved re-requests); (2) a `newNoData` resync no longer wipes the `carryOver` queue, so scattered single-serial drops keep being re-requested instead of being silently abandoned and scattered across the whole recording (#43/#46). The final polling cycle's received packets are no longer discarded on `stop()`.

### Fixed

- Drop cached GATT characteristics when the link is down so auto-reconnect after a physical disconnect (out of range) no longer fails forever on stale characteristics from the previous connection (regression introduced by the per-UUID characteristic cache).
- Keep GATT characteristics per UUID (`_characteristics` map) so calling `getDeviceInformation()` / `setDataStreamingMode()` / `syncCoreTime()` while SENSOR_VALUES notifications are active no longer risks attaching or detaching the notify listener on the wrong characteristic. `dataCharacteristic` is kept as "last touched characteristic" for backward compatibility.
- Normalize `setup()` options so partial or empty options objects do not throw and interpolation defaults are preserved.
- Handle `serial_number` wraparound from `65535` to `0` without false `lostData()` callbacks, including after `clear()`.
