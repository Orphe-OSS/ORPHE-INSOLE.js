FIFOとは（かんたん解説）

Realtime（垂れ流し）

INSOLE が計測したデータを、そのまま次々に送ってきます（push）。

  • 遅延がとても小さい。可視化やゲームに向く
  • クォータニオン（姿勢）も取れる
  • 電波で取りこぼしたデータは、もう戻ってこない

「多少抜けてもいいから今すぐ欲しい」用途向け。

FIFO（いったん貯める）

INSOLE が計測データを本体の中にいったん保存し、PC側が 「serial番号 ○番から○個ください」と指定して取り出す方式です（pull）。

  • 通信が一時的に遅れても、届かなかったserialを再要求して埋められる
  • 停止したあとも、まだ本体に残っている分をdrain（回収）してから記録完了になる
  • データはまとめて届くので、画面はカクカク更新される

「あとで解析するから抜けを減らしたい」用途向け。

端末内バッファは約30秒分

ORPHE INSOLE の FIFO バッファが保持できる長さは約30秒分です。 SDK の実装定数から次のように換算しています（src/InsoleFifo.js）。 

1 serial packet = 4 frame × 5 ms          = 20 ms
バッファ上限     = 1500 packet (RING_BUFFER_CAPACITY)
保持できる長さ   = 1500 × 20 ms = 30,000 ms  ≒ 30 秒
（別の言い方: 200 sample/s ÷ 4 sample/packet = 50 packet/s → 1500 ÷ 50 = 30 s）
  • 30秒以内の短時間計測は、計測区間の全体が端末内バッファに収まりやすいため、 安定した記録に向いています。
  • 30秒を超える計測も可能です。ただし接続するPCの性能・Bluetooth環境・ 他のBLE機器との競合・タブのバックグラウンド化などで 回収速度が生成速度に追いつかないと、古いデータが上書きされ回復不能な欠損になります。
  • 「30秒以内なら絶対に無欠損」という保証ではありません。 30秒以内でも回収が滞れば欠損しますし、逆に30秒を超えても追いつけていれば欠損しません。 長時間計測では必ずこのページの欠損表示と、保存したCSVの中身を確認してください。

収録中は lag（まだ取り出せていないserial数）が上限 1500 に近づくほど危険です。 このページでは最大lagも表示します。

混同しやすい3つのポイント

① dropped と CSVの missing は別の指標

  • dropped … 収録中に「もう取り戻せない」と判断された累計イベント数。 再同期やバッファ上書きのたびに加算されます。プレビュー中の分や、あとから再要求で回収された分の 数え方の違いで、最終的なCSVの欠損数と一致しないことがあります。
  • missing … 保存されるCSVの区間（正式計測の開始〜drain完了）で、 expected に対して実際に足りなかった serial 数。CSVの中身と直接対応します。
  • 合否は missing と dropped の両方が 0 かどうかで判断してください。

② CSVの1行 ≠ FIFOの1 serial packet

1つの serial packet には 4フレーム（5ms間隔）が入っています。 CSVはフレーム単位で書き出すので、1 serial = 4行になります。 「CSVが4000行あるのにserialが1000しかない」のは正常です。 欠損を数えるときは行数ではなく serial 番号の連続性を見てください。

③ FIFO Raw に入るもの・入らないもの

  • 入る: ジャイロ・加速度・6ch圧力
  • 入らない: クォータニオン（姿勢） — 姿勢が必要なら Realtime を使ってください
  • 現行ファームウェアでは FIFO Raw と Step Analysis は同時に取得できません。 「FIFOで収録 → 止めてから Step Analysis」のように順番に使ってください。
